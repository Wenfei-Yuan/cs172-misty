# Refactor an existing repo
**DO NOT TRY TO COMMIT CHANGES TO GITHUB**
**DO NOT WRITE SPAM FILES INTO THE REPO**
**DO NOT USE SUDO**
inputs:
input 1: target refactor functionalities, repository, or scripts
input 2: target files (optional)
input 3: target repo (optional)
Inputs specify the refactor targets. 

**read through this entire file and follow the instructions carefully**. 

When ask to refactor existing functionalities, repositories, and scripts, always, first read the following files @.github/instructions/repo_info (REFER AS KEY MD FILES):
1. codebase_overview.md
2. scripts_overview.md
3. update_logs.md
4. known_issues.md
Understand them, and keep them inside the memory. 


#CREATE ONE TODO FOR EACH OF THE FOLLOWING STEPS
then, for refactoring existing functionalities, repositories, and scripts, **CREATE ONE TODO FOR EACH STEP**:
1. if input 1 or input 2 are specified in the inputs, the main agent should read through the files associated with the inputs, and understand them. then combine the understood knowledge with the key md files. 
2. the main agent should create five subagents and let them work parallel (plan agent, architecture improvement; plan agent, redundancy reduction; plan agent, robustness improvement; plan agent, free mode; code agent, senior engineer, code review;), pass the input information to the five subagents. The five subagents should be **launched paralelly**. The five subagents should read through the key md files. Then:
a. the plan agent for architecture improvement should first process the refactor targets and the key md files. Then based on the current code/repo/architecture and the input refactor targets, the subagent should analysis: 1) what functionalities and scripts should be refactored and why they should be refactored; 2) what functionalities are inappropriately designed/placed in the existing codebase and why they are inappropriately designed/placed; 3) how to improve the code architecture of the existing codebase/scripts and what are the improvements compared to the current code architecture. Then,  based on the analysis, the subagent should draft an initial plan, including what can be improved, why should they be improved, and what are the consequnce of the improvements. Based on the initial plan, the subagent should read through the associated files and scripts, specifically focus on validating and improving the intial plan. Then, based on the file reading, the subagent should finalize the initial plan that improves the architecture of the existing codebase/scripts/functionalities, and then draft a comparison statement that shows how the code architecture is improved based on the original codebase diagram. The pan should keep the entire codebase performs stable, not introducing any new bugs, and would not repeate any known issues/bugs in known_issues.md. then the subagent feeds the plan and the comparison statement back to the main agent as [plan 1] and [comparison statement 1].

b. the plan agent for redundancy reduction should first process the refactor targets and the key md files. Then based on the current code/repo/architecture and the input refactor targets, the subagent should analysis: 1) what functionalities and scripts have redundancy and why they have redundancy; 2) are there any overlapped implementations in the existing codebase/scripts/code and why they have overlapped implementations; 3) how to reduce the redundancy of the existing codebase/scripts and what are the improvements compared to the current codebase/scripts. Then, based on the analysis, the subagent should draft an initial plan, including what can be improved/removed, why should they be improved/removed, and what are the consequnce of the improvements/removements. Based on the initial plan, the subagent should read through the associated files and scripts, specifically focus on validating and improving the intial plan, imagine what would happen if the planned redundancies are removed. Then, based on the file reading, the subagent should finalize the initial plan that reduces the redundancy of the existing codebase/scripts/functionalities, and then draft a comparison statement that shows how the redundancy is reduced based on the original codebase/scripts. The pan should keep the entire codebase performs stable, not introducing any new bugs, and would not repeate any known issues/bugs in known_issues.md. then the subagent feeds the plan and the comparison statement back to the main agent as [plan 2] and [comparison statement 2].

c. the plan agent for robustness improvement should first process the refactor targets and the key md files. Then based on the current code/repo/architecture and the input refactor targets, the subagent should analysis: 1) what functionalities and scripts have robustness issues and why they have robustness issues; 2) are there any potential bugs or issues in the existing codebase/scripts/code and why they have potential bugs or issues; 3) how to improve the robustness of the existing codebase/scripts and what are the improvements compared to the current codebase/scripts. Then, based on the analysis, the subagent should draft an initial plan, including what can be improved, why should they be improved, and what are the consequnce of the improvements. Based on the initial plan, the subagent should read through the associated files and scripts, specifically focus on validating and improving the intial plan, imagine what would happen if the planned improvements are implemented. Then, based on the file reading, the subagent should finalize the initial plan that improves the robustness of the existing codebase/scripts/functionalities, and then draft a comparison statement that shows how the robustness is improved based on the original codebase/scripts. The pan should keep the entire codebase performs stable, not introducing any new bugs, and would not repeate any known issues/bugs in known_issues.md. then the subagent feeds the plan and the comparison statement back to the main agent as [plan 3] and [comparison statement 3].

d. the plan agent in free mode should first process the input information and the key md files. Then the subagent should decide what files to read and what scripts to check, based on the known information. Then analysis what the refactor targets, how to refactor the existing codebase, and what scripts and files could be associated with the refactor targets. Then, the subagent should draft a plan that refactors the existing codebase while maintaining the entire codebase performs stable. then the subagent feeds the plan and the implementation diagram back to the main agent as [plan 4].

e. the code agent for senior engineer code review should first process the refactor targets and the key md files. Then based on the input information, the plan, and the repo structure based on the key md files, decide a list of files and scripts that could be associated with the input and the refactor targets as [associated files]. Then, the subagent should start reading files **LINE BY LINE** from the [associated files] from a senior engineer perspective. While reading, if any files or scripts are found to be highly associated with the refactor targets, add them to the [associated files] and read through them as well. After finishing reading one file from the [associated files], add the read file into [read files]. Once the [read files] and [associated files] are the same, the reading is finished. Then, based on the reading, the subagent should review the code from a senior engineer perspective, find out what are not good in terms of code quality, readability, maintainability, and robustness. Then draft a code review report that includes what are the issues in the existing codebase/scripts/functionalities as [code issue review report], and what can be improved, why they should be improved, and how to improve them as [code improvement reviw report]. 
Then the subagent feeds the two review reports back to the main agent as  [code issue review report] and [code improvement reviw report].

3. the main agent creates a subagent (plan agent, principal engineer role), pass the refactor targets and all the plans ([plan 1], [plan 2], [plan 3], and [plan 4]), the comparison statements ([comparison statement 1], [comparison statement 2], and [comparison statement 3]), and the code review reports ([code issue review report] and [code improvement reviw report]) from the other subagents and input information to this subagent. The subagent should additionally read through the key md file and all scripts in this repo to get a comprehensive understand of the entire repo. If the plan involves any repo outside this repo, go to that repo, if there are codebase_overview.md and scripts_overview.md, read through them too. Then the subagent reviews all plans, comparison statements, and code review reports based on the information it has from a principal engineer perspective, assess the plans', comparison statements', and code review reports' correctness and feasibility, rejecting redundant or incorrect plans, making sure that the plan can 100% achieves the refactor targets without breaking the current codebase. feed the review back to the main agent as [plan review].

4. the main agent reviews all the plans ([plan 1], [plan 2], [plan 3], and [plan 4]), the comparison statements ([comparison statement 1], [comparison statement 2], and [comparison statement 3]), the code review reports ([code issue review report] and [code improvement reviw report]) from step 2 and the [plan review] from step 3. If the plans, comparison statements, code review reports, or the review involves any other repos, go to those repos, read their codebase_overview.md and scripts_overview.md if exist, and keep those in the memory. Finally, combine all those information and draft a final plan that is feasible, stable, and 100% correct. Then the main agent should go through the final plan. For each step in the final plan, read through the associated codes and scripts, imagine what would happen if the step is implemented, and exam the correctness and make sure the changes would not break the current codebase. If any step in the final plan is found to be problematic, revise the final plan accordingly, and make sure the revised [final plan] can 100% achieve the refactor targets without any issues.

5. the main agent creates a subagent (devil's advocate), pass the [final plan] and the input functionalities to the subagent. The subagent should read through the key md files and all relevant scripts, then critically challenge the plan — looking for overlooked side effects, integration risks, incorrect assumptions about the codebase, or potential regressions. The subagent reports any flaws back to the main agent. The main agent incorporates valid criticisms and updates the [final plan] accordingly. 

6. Then, the main agent should print the updated [final plan], so the user can read it later. **If the user has requested for no code changes, THE MAIN AGENT SHOULD STOP AFTER PRINTING THE FINAL PLAN. OTHERWISE, KEEP PROCEEDING TO STEP 7**. If the user has NOT SPECIFIED or requires code changes, the main agent should continue to step 7.

7. the main agent creates a subagent (code agent), pass the [final plan] and the refactor targets to the subagent. The subagent should also read through the key md files. Then based on the the [final plan] and the refactor targets 
 read all scripts that are associated with the [final plan]. Then subagent start implementing the plan and achieve the refactor targets accordingly. After finishing the implementation, the subagent shuold generate a [implementation report] (just what has been changed, **no explanation**), and report the [implementation report] back to the main agent. 

8. the main agent creates two subagents and let them **WORK IN PARALLEL** (code agent, senior staff engineer role; code agent, QA engineer role). Then:
a. the main agent should pass the [final plan], refactor targets, and [implementation report] to the code subagent: senior staff engineer role. The subagent should additionally read through the key md files and check all the code changes in the repo. Then the subagent reviews the code changes and the implementations from a senior staff engineer perspective, assess the code implementation correctness, making sure that the new functionalities are 100% achieved without breaking the current codebase. Then the subagent should generate a [refactor code review report] and then feed the review back to the main agent as [refactor code review report].

b. the main agent should pass the [final plan], refactor targets, and [implementation report] to the code subagent: QA engineer role. The subagent should additionally read through the key md files and check all the code changes in the repo. Then the subagent read through the entire repo pipeline, validate: 1. if the entire repo still performs correctly; 2. if the refactored functionalities perform as expected with 0 error. Based on the validation, the subagent should generate a [refactor code QA report]. If the user has requsted to actually **run the scripts**, the subagent should run through the entire codebase pipeline based on the codebase_overview.md and scripts_overview.md from upstream to downstream, and validate if the entire repo still performs correctly and if the refactored functionalities perform as expected with 0 error. Then, the subagent should update the [refactor code QA report] based on the running results, and then report the [refactor code QA report] back to the main agent as [refactor code QA report].


9. the main agent should read through the [final plan], the [implementation report], the [refactor code review report], and the [refactor code QA report], then understand the code changes, the implementation, and the refactors to the codebase. Then, the main agent should according update the codebase_overview.md and scripts_overview.md based on the refactor targets and the actual code changes (including the failures based on the the [refactor code review report], [refactor code QA report]).

10. the main agent should summarize the refactor changes in the following format:
{=============================Refactor Update===============================}
{Refactor Summary (very high level description of the refactor target) and refactor Id (assign a number in order, i.e., plus 1 to the last refactor id)}
{Refactor description (one or two sentences of description of what the refactor is)}
{Repo involved (what local repos are involved)}
{Implementation ( what has been implemented to achieve the refactor)}
{Achived (whether the refactor has been achieved, if not achieved, what is the gap)}

11. write the Refactor Update summary to update_logs.md. do not add additional contents, just the refactor update report from previous step. In addition, summarize the refactor changes in bullet points and write them to the chat.
